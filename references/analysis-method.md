# 分析方法（analysis-method）

脚本只负责"事实骨架"（时间、去重、统计、原文引用）。本文件规定 Agent 如何把骨架变成对用户有用的判断。

## 1. 分析目标

用户真正要的不是"一堆笔记摘要"，而是三个问题的答案：

1. 这家公司/这个岗位**现在**怎么面？（流程、轮次、间隔、重点）
2. 我**大概率**会被问什么、卡在哪？（高频问题、硬门槛、避雷点）
3. 我**现在**能投哪些、怎么投？（在招帖、匹配度、话术）

报告必须先给结论，再给证据。

## 2. 两种时间线

不要混为一谈，报告里分开呈现。

### 2.1 发布时间线（`published_at`）

- 用途：判断信息新鲜度、流程是否改版、HC 是否收紧。
- 排序：默认按 `published_at` 倒序（最近在前）。
- 近 3 个月 / 3-12 个月 / 更早，分三档标注。
- 若同一企业近 3 个月出现"流程变短/变长"的集中描述，必须单独提示。

### 2.2 流程时间线（单篇笔记内部）

从正文抽取"投递 → 笔试 → 一面 → 二面 → 三面 → HR 面 → OC/挂"的事件序列，并计算相邻事件间隔（天）。

```text
9.12 投递 → 9.18 一面（+6）→ 9.25 二面（+7）→ 10.8 OC（+13），全程 26 天
```

规则：

- 只使用笔记中**明确出现**的日期或间隔（"隔了 3 天""一周后"）。
- 日期缺年份时，按笔记发布时间推断，并标注"推断"。
- 同一轮次出现多个日期时，保留区间（"一面 9.18-9.22"）。
- 不得把不同笔记的日期拼成一条个人流程线。跨笔记只做**统计**（如"投递到一面中位数 5 天，样本 6"）。

### 2.3 排序键

| 场景 | 排序 |
|---|---|
| 看最新动态 | `published_at` 倒序 |
| 复现完整流程 | 流程事件正序（时间推进） |
| 找高频问题 | 提及次数倒序，次数相同按点赞加权 |
| 找在招岗位 | 发布时间倒序 + 互动量 |

`published_at=null` 的帖子不进主时间线，也不进在招主清单，放"时间未知，需人工确认"分组（`plan.json` 的 `undated_jobs`）。

## 3. 归属判定

一条笔记可能同时提到多家公司（"字节 vs 腾讯 后端面经对比"）。

- 主归属：标题或首段明确指向的企业。
- 次归属：正文用独立段落/轮次描述的企业，标 `secondary`。
- 只作对比提及时，不归入目标企业的主样本，只进"横向对比"。
- 无法判定归属的笔记，进"未归类"，不要硬塞。

岗位归属同理：区分"后端/客户端/算法"等方向，避免把算法岗面经混进后端结论。

## 4. 面经提炼维度

对每家企业产出一张卡片，字段固定：

| 维度 | 内容要求 |
|---|---|
| 流程 | 轮次、顺序、是否有笔试/群面/HR 面 |
| 间隔 | 各环节等待天数，给中位数和样本量 |
| 形式 | 电话/视频/现场、是否有手撕、是否共享屏幕 |
| 高频问题 | 按主题聚类（基础、项目、算法、系统设计、行为面），每条附原文与来源数 |
| 硬门槛 | 学历、语言、年限、专业等明确写出的限制 |
| 结果信号 | OC/offer/池子/挂，以及"泡池子""海投"等描述 |
| 薪资口径 | 只记录笔记中出现的口径，标"网传/个例"，不当结论 |
| 避雷点 | 加班、PUA、流程拖、岗位与实际不符等 |

**只引用原文**。不要补写笔记里没有的面试题，哪怕"这类岗位通常会问"。若要补充常识性建议，必须放在"通用建议"区并明确标注不是来自本次采集。

## 5. 评论区处理

评论区往往是信息密度最高的地方，也最容易混入广告。

### 5.1 分层

| 层 | 判定 | 用途 |
|---|---|---|
| 补充面经 | 含轮次、题目、时间、结果描述 | 并入高频问题与流程证据 |
| 共识/反驳 | 多人重复同一说法，或明确"我面的时候不是这样" | 标注一致 / 矛盾 |
| 结果播报 | "已 OC""同批挂了" | 估计节奏与竞争度（仅趋势，不精确率） |
| 提问 | "求问二面多久出结果" | 识别用户的真实焦虑点，可写入报告"待确认项" |
| 噪声 | 含"加微信""私信我""付费""内推收费""代写""简历修改" | 剔除，不出现在结论里 |

### 5.2 噪声识别

脚本已按关键词打 `noise_flags`，Agent 仍需人工判断：

- 真内推：正文有公司/部门/岗位/投递邮箱或官方链接，且不收费。
- 假内推：只留微信、要求付费、承诺"包过"、无具体岗位。→ 剔除并在报告"风险提示"里点名类型，不点名账号。
- 引流号：同一账号在多个不相关帖子下重复同一话术。→ 剔除。

### 5.3 引用规则

- 引用评论时给"来源笔记 + 评论赞数"，不要只写"网友说"。
- 单条评论不能作为结论，至少 2 条独立来源或 1 条高赞 + 正文互证。
- 昵称默认保留；用户要求匿名时用 `用户A/用户B`。

## 6. 可信度分级

| 等级 | 条件 | 报告写法 |
|---|---|---|
| 高 | ≥3 篇独立笔记一致，含具体时间/题目/结果 | 直接陈述 |
| 中 | 1-2 篇，或多篇但细节少 | "据 N 篇笔记" |
| 低 | 单条评论、无来源、明显情绪化 | "有个例提到"并标注不确定 |
| 冲突 | 多篇结论相反 | 并列呈现两种说法 + 各自样本量 |

冲突时不取平均、不投票，直接把分歧写给用户，并说明可能原因（部门/年份/岗位不同）。

## 7. 报告结构

严格按 `assets/report-template.md`：

1. **结论摘要**（≤150 字）：这家公司现在怎么面、你匹配度如何、建议投哪几个
2. **企业卡片**：流程时间线（图或表）→ 高频问题 → 评论区洞察 → 避雷点 → 可信度
3. **在招岗位表**：岗位、地点、发布时间、匹配分、联系方式（待核实）、链接
4. **投递清单**：优先级、话术、缺口技能
5. **数据与方法**：采集时间、关键词、样本量、覆盖率、无法核实项、手动回填比例

## 8. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 把单篇笔记当公司标准流程 | 误导用户 | 标注样本量 |
| 用模型常识补面试题 | 用户按错误重点准备 | 只用原文，常识另开区块 |
| 把"薪资 30k"写成结论 | 用户预期失真 | 标"个例/网传"，给区间 |
| 时间线倒挂（OC 在投递前） | 报告不可信 | 检查日期年份推断 |
| 只写"竞争激烈"这类空话 | 无行动价值 | 给具体轮次、间隔、题目分布 |
| 把广告内推当岗位推荐 | 用户被引流 | 噪声剔除 + 风险提示 |

## 9. 输出给脚本的部分

以下由脚本完成，Agent 不要手工算：

- 相对时间 → 绝对时间
- 去重
- 点赞/收藏统计
- 关键词命中与匹配分
- 样本量、覆盖率
- 报告骨架（表格与占位）

Agent 只做：归属判定、语义聚类、可信度评级、结论撰写、风险判断。
